# Profile Card Alignment Design

Date: 2026-08-14
Repository: `Vikbg/Vikbg`

## Goal

Replace the current mixture of hardcoded SVG dot leaders and special-case alignment logic with one reusable alignment system for the profile card.

The resulting system must keep the visual layout aligned automatically when labels or values change. It must work for both `dark_mode.svg` and `light_mode.svg`, preserve the current terminal-style appearance, and keep the existing GitHub Actions workflow compatible.

## User-visible success criteria

1. Every simple profile row uses computed dot padding rather than manually maintained dot counts.
2. Values within the same visual group end at a consistent target column.
3. GitHub Stats rows remain aligned when counts grow or shrink.
4. The final `)` of the GitHub LOC row stays aligned with the right edge of the reference stats row.
5. The LOC deletion value never receives dot padding between the comma and the minus sign.
6. The same alignment behavior is applied to both SVG themes.
7. Changing a static value such as a language list, hobby, email address, IDE string, or portfolio URL does not require manually recounting dots.
8. No U+2014 character is present in any file modified by this work, including comments, docstrings, Markdown, Python, tests, and SVG content.

## Current state

The repository currently has three alignment mechanisms.

First, several dynamic GitHub statistics use `justify_format()` and fixed width constants in `today.py`.

Second, two-column GitHub statistics use additional helpers such as `secondary_stat_gap()`, `repo_stats_left_width()`, and `commit_stats_left_width()`.

Third, `generate_readme.py` currently wraps the base generator with LOC-specific logic that recalculates `loc_data_dots` so the final LOC parenthesis aligns with the stats rows.

Most non-stat rows still store literal dot leaders directly in the SVG templates. This includes OS, Host, Kernel, IDE, Languages, Hobbies, and Contact rows. Their alignment therefore depends on manually edited dot counts.

The SVG section separators also contain U+2014 characters, which conflicts with the new repository constraint for modified files.

## Chosen architecture

Use a generic SVG alignment engine in Python and treat both SVG files as templates with identifiable alignment fields.

The alignment engine has two responsibilities:

1. Replace dynamic values when needed.
2. Recompute dot leaders from the actual visible text and a target visual width.

The SVG templates continue to own visual content and theme colors. Python owns spacing calculations. This avoids generating the whole card from Python while removing manual dot maintenance.

## Alignment model

### Simple rows

A simple row has these conceptual pieces:

```text
. <label>:<dot leader><value>
```

For a simple row, the generator computes:

```text
padding_width = target_row_width - prefix_width - value_width
```

where:

- `target_row_width` is the desired visible width of the row or group.
- `prefix_width` includes the leading `. `, the complete label, punctuation, and any fixed text before the dot leader.
- `value_width` is the visible character length of the current value.
- the dot leader is generated by one shared helper from `padding_width`.

The helper must preserve the current visual convention of surrounding longer dot runs with spaces.

If a value is too long for the target width, the generator must not create negative padding. It returns the minimum valid separator and allows the row to extend to the right. This avoids malformed output and keeps the failure mode readable.

### Groups

The following groups share a common right-edge target:

- System info: OS, Uptime, Host, Kernel, IDE.
- Languages: Application, Systems, Spoken.
- Hobbies: Software, Hardware, Science.
- Contact: Portfolio.Link, Email.Work, Instagram, Discord.

Each group target is defined centrally in Python. The implementation should prefer named constants or a small configuration mapping over scattered numeric arguments.

The values can remain in the SVG for static rows. The generator reads their current text from the XML, computes the correct dot leader, and writes the adjusted padding back.

Dynamic rows such as Uptime continue to have their value replaced before alignment is calculated.

### GitHub Stats

GitHub Stats keeps its special content structure but uses shared primitives for width measurement and dot leader generation.

The first row is conceptually:

```text
. Repos:<dots><repos> {Contributed: <contrib>} | Stars:<dots><stars>
```

The second row is conceptually:

```text
. Commits:<dots><commits> | Followers:<dots><followers>
```

The implementation keeps the second column separator but computes its position from the rendered width of the left side. Existing constants that describe meaningful target columns may remain, but manual dot counts must not remain in the SVG.

The LOC row is conceptually:

```text
. GitHub LOC:<dots><net> ( +<added>, -<deleted> )
```

Its final width is calculated from the complete rendered row. The dot leader before the net LOC value is then selected so the final `)` reaches the same target right edge as the reference stats row.

`loc_del_dots` is no longer used for visual padding. If the node is retained for compatibility, its text must always be empty.

## SVG template changes

Every dot leader that should be calculated at runtime receives a stable `id`.

Recommended naming convention:

```text
<field>_dots
```

Examples:

```text
os_dots
host_dots
kernel_dots
ide_dots
languages_application_dots
languages_systems_dots
languages_spoken_dots
hobbies_software_dots
hobbies_hardware_dots
hobbies_science_dots
portfolio_dots
email_dots
instagram_dots
discord_dots
```

Static values that need to be read for alignment do not strictly require new ids if the code can reliably locate the corresponding row. However, stable ids on value nodes are preferred because they make the template explicit and easier to test.

The two SVG themes must use the same ids and structural layout so the same Python code can process both files.

All U+2014 separator characters in modified SVG content are replaced with ASCII hyphen characters. This applies to the profile header separators, Contact separator, and GitHub Stats separator.

## Python design

### Shared dot leader helper

Keep one function responsible for converting a requested visible padding width into the dot leader string.

The function must handle:

- width less than or equal to zero.
- width 1.
- width 2.
- normal widths greater than 2.

No other function should manually build repeated dot strings for profile rows.

### Row measurement helper

Introduce a helper that measures visible text length from explicit pieces rather than from raw XML serialization.

Its input should be the visible prefix, current value, and optional suffix. Its output is an integer character width.

This keeps the calculation independent from XML tags and CSS classes.

### Simple alignment helper

Introduce a helper with a responsibility similar to:

```text
align_value_row(root, dots_id, prefix_text, value_text, target_width)
```

The exact function signature may change during implementation, but it must have one clear purpose: calculate and write the dot leader for one row.

The helper should not fetch external data or modify unrelated SVG nodes.

### Group configuration

Represent simple static groups in a compact configuration structure. Each entry identifies:

- the dot node id.
- the value node id or other stable value source.
- the visible prefix used for width calculation.
- the target group width.

This prevents a long series of nearly identical function calls and makes future profile edits easy.

### Dynamic data integration

Dynamic data replacement happens before the final alignment pass.

Recommended render sequence:

1. Parse SVG.
2. Replace dynamic values.
3. Compute two-column stat spacing.
4. Align all simple rows from their current values.
5. Align the LOC row from the final compact LOC values.
6. Write SVG.

This order ensures spacing always uses the final text that will be rendered.

### `generate_readme.py`

The current LOC-specific monkey patch should be reduced or removed once the generic behavior lives in the core renderer.

`generate_readme.py` should remain focused on GitHub Actions-safe data acquisition and delegating rendering to `today.py`.

If compatibility requires a small wrapper, it must not duplicate alignment algorithms.

## Error handling

Missing required template ids should fail clearly during development and tests rather than silently producing misaligned output.

A dedicated lookup helper may raise a descriptive exception when an expected alignment node is absent.

Optional compatibility nodes such as `loc_del_dots` may be handled separately if they are intentionally allowed to be absent.

Alignment functions must clamp negative computed padding to a safe minimum instead of producing invalid repeated-string operations.

## Tests

Add a focused automated test module for alignment behavior.

The tests should avoid network access. They should test pure formatting and local SVG rendering behavior.

Required cases:

1. Dot leader generation for padding widths 0, 1, 2, and a normal larger width.
2. A short value causes more dots.
3. A longer value causes fewer dots.
4. A value longer than the target width does not crash and does not create negative padding.
5. Repos and Stars stay aligned for small and large values.
6. Commits and Followers stay aligned for values such as 9, 99, 999, 1,000, and 100,000.
7. LOC alignment works for small and large net, added, and deleted values.
8. LOC deletion formatting remains `, -VALUE` with no dot leader before the minus sign.
9. Languages alignment survives a longer technology list.
10. Contact alignment survives a longer email or portfolio value.
11. Dark and light SVG templates expose the same required alignment ids.
12. Generated or modified target files contain no U+2014 character.

Tests should compare computed visible widths, not screenshots. A screenshot or manual profile inspection can be used as a final verification step, but it is not the primary correctness test.

## Verification workflow

Implementation is not complete until all of the following checks pass:

1. Run the alignment unit tests locally or through an equivalent executable test path.
2. Render both SVG themes with representative current values.
3. Render with artificial long and short values to verify automatic expansion and contraction of dot leaders.
4. Confirm the right edges of grouped rows are equal by computed visible width.
5. Confirm the LOC final parenthesis has the same computed target edge as the reference stats row.
6. Search every modified file for U+2014 and require zero matches.
7. Review the Git diff for accidental text or value changes unrelated to alignment.
8. Commit the implementation.
9. Let the GitHub Actions workflow regenerate the SVGs.
10. Fetch the final generated SVGs from `main` and verify that the dynamic run preserved the alignment rules.
11. Check the workflow result or resulting commit before claiming completion.

## Self-review requirements during implementation

The implementation plan must contain explicit review checkpoints.

### Review 1: Core algorithm

After the shared helpers are implemented, check for duplicated dot generation, magic values, off-by-one calculations, and unclear naming.

### Review 2: Template migration

After SVG ids and separators are migrated, compare dark and light templates and verify their required ids are structurally identical.

### Review 3: Tests

Before implementation is considered complete, inspect whether the tests cover both shrinking and growing values, overflow behavior, LOC formatting, theme parity, and the U+2014 constraint.

### Review 4: Final diff

Inspect all modified files for unrelated edits, stale special cases, accidental value changes, and prohibited U+2014 characters.

### Review 5: Post-workflow result

After GitHub Actions runs, fetch the generated SVGs and verify that the workflow did not restore old dot counts, old separator characters, or LOC-specific artifacts.

## Scope boundaries

This change does not redesign the visual card, change colors, change fonts, add new profile fields, change GitHub statistics semantics, or change how LOC is calculated.

It does not move the entire SVG generation into Python.

It does not change the profile content except where ASCII hyphen separators are required by the character constraint.

The work is limited to alignment infrastructure, template identifiers, tests, removal of obsolete alignment special cases, and verification tooling needed to support those changes.

## Expected files

The implementation is expected to touch at least:

```text
today.py
generate_readme.py
dark_mode.svg
light_mode.svg
```

It should also add a focused test file. The exact test path will be selected in the implementation plan after checking the repository's current test conventions.

No unrelated files should be modified unless the implementation plan identifies a concrete dependency and explains why it is necessary.
